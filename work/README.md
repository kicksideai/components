# kickside/work

Work tracking on KickSide threads: boards of typed items, process transitions, hierarchy, relations, comments, rank and rollups. Each board owns a component, its event log and a projected read model.

Call `kickside.work:board` through the default service binding. HTTP handlers expose the same service under `/work/boards`. Component ACLs gate each operation; private producer policies reserve durable facts for validated commands and jobs.

- `kickside.work.domain`: schema, process, value forms, filter tree, predicates, layout, plugin manifests, rank and rollups.
- `kickside.work.persist`: repositories, generated tables, bulk writes, the threads client and event projection.
- `kickside.work.command`: prepare, apply, schema commands, query-driven bulk, cross-board moves and board creation.
- `kickside.work.read`: item, query compiler, scopes, history and changes views.
- `kickside.work.service`: validated contract boundary.
- `kickside.work.jobs`: migration, rank rebalance, rollup recompute, index rebuild, state timers, cross-item advance, captured-caller bulk and move completion.
- `kickside.work.retention`: bounded trash purge, age retention, teardown continuation and orphan prefix release.

The initial migration creates the Work and template tables, including the ordered link-page indexes. Saved views record their anchor board in Component metadata at creation. A rejected move can release its caller key while retaining its operation ID. Existing development installations need a fresh Work schema. [Migration declaration](src/migrations/_index.yaml)

The host supplies the database, authenticated API router and prefix-registry administrator grant. Board creation requires the Work administration capability. Work requires Component 0.3.28 or newer. The board kind is closed. Exact create/update grants belong to Work's creation, pack execution and public metadata frames. Generic registration and context/meta mutation outside Work admission are refused. Ordinary Component access governs board placement, ancestor relocation and folder deletion with `reparent_root`. Component registration atomically stores a durable creation fingerprint with the board; failed admission creates no Work receipt. Retries compare that fingerprint independently of editable title and placement. Successful initialization stores its result beside the fingerprint; identical retries return that result without replaying the declaration, even after ordinary receipts expire. A fingerprint without a completion result denotes interrupted initialization, which resumes through the keyed schema or pack operation. Schema apply requires the registry grant when claiming a prefix.

`list({limit?, after?})` returns at most 50 boards and a `next` continuation. Pass `next` as `after` to continue through HTTP or `WorkListBoards`. Counts use caller-visible items and the same visibility-index rebuild fence as queries; public component metadata contains no population counts.

Board discovery, saved-view listing and pack fleet listing page by offset over live Component results. Inserts, deletes or access changes before the offset can repeat or skip entries between calls. Restart from the first page to refresh a traversal.

A successful `create` always establishes an initial schema generation. Omitting `declaration` creates an empty declaration with prefix `W` followed by the first nine hexadecimal characters of the deterministic board ID, uppercased. Work checks the first declaration and whether its prefix is already held before registering the board. The versioned claim on schema apply arbitrates concurrent registrations with the same prefix. Existing schema-less boards and interrupted initializations can apply their first declaration at expected generation 0.

The board contract covers board and schema administration, pack installation, item commands, queries, history, plugin configuration, bulk operations and moves. [Methods and request schemas](src/contracts/board.yaml)

Board list entries and item get/explain results include independent `access: {read, write, delete, admin}` booleans for the caller. Item delete, restore and cross-board moves also require WRITE and pass the ordinary command checks. Explain includes the database planner’s selected index names and `budget: {rows_scanned, rows_remaining, deadline_remaining_ms}`; it plans without scanning item rows. Each HTTP operation owns a handler and endpoint entry. Shared model types live at `kickside.work:types`.

Reads return committed snapshots. An authorized reference to a component of another kind returns `NOT_FOUND` with code `board_not_found`. A `min_seq` beyond the snapshot returns a retryable `UNAVAILABLE` error with code `projection_pending`. Deferred workers resolve the stored board identity and bound projection waits by the enclosing job deadline. Retention reports each blocked prefix and continues processing the batch.

Schema plan and apply retain the existing visibility rule when `visibility` is omitted. Send `remove: { visibility: true }` to clear it as a reviewed semantic change. A declaration can either set or remove the rule in one request. Pack upgrades retain their separate visibility-removal refusal.

Write acknowledgement waits for the request's committed board sequence. Independent apply uses the highest committed group sequence. Replay can return a projected receipt immediately. When a needed receipt is missing, Work waits for the thread head sampled at catch-up entry and reads the receipt again.

`update({board_id, title?, description?, icon?})` edits component metadata under board ADMIN, independently of READ or WRITE. Omitted values stay; empty descriptions and icons clear those properties. Titles are nonblank text of at most 255 bytes. Supplying `key_prefix` returns `invalid` with `prefix_immutable`. The result reports `status: updated` or `status: unchanged`; unchanged requests append no event. Each edit records `kickside.work.events:board.updated`, whose closed schema binds `output_kind` to the board binding, and exposes `kickside.work.ports:board_updated`. The board projection and public meta publisher retain these edits before and after the first schema. Board list entries and item get results include board title, description and icon. HTTP uses `POST /work/boards/{id}/update` under the administration endpoint policy.

Packs are caller-visible `registry.entry` declarations with `meta.type: kickside.work.pack` and title, version, icon and description metadata. Their data contains `schema`, optional `processes`, shared `views`, `automations`, `traits`, `starter: {items, default}` and `requires` naming exact plugin manifests. `GET /work/packs` lists their canonical data digests and whether each required plugin is available under the caller's scope. Discovery includes the display title and configuration schema for each available plugin when its manifest declares them. Invalid declarations remain identifiable entries with a structured `problem` and cannot install. Pack schema lists use the declaration contract’s list shapes. A top-level process list replaces the nested list and is validated before merge or state-map planning. Pack view definitions use the closed saved-view create request shape. Pack planning checks each resolved view's type, configuration and query against the proposed schema before recording provenance. Pack modules grant their exact entry ids; Work grants no wildcard access to external declarations. Registry declarations canonicalize integral numbers at their read boundary before strict declaration validation. Pack digests and outdated checks use that same representation; fractional counts retain their condition errors.

`pack_plan({board_id, pack, version?, expected_generation})` requires board ADMIN and plans an install on an empty unprovenanced board or a three-way upgrade from its stored pack base. It returns ordinary schema classifications and migration paths, local conflicts, proposed state maps, shared views, automations, traits and plugin activations. Apply requires an explicit `maps` decision for state removals and `resolutions[path]: local | incoming` for conflicts. Missing plugins return `unknown_plugin`; another installed version returns `pack_version_unavailable`. Managed resource removal requires the plan's migration path.

`pack_apply` adds `key` and optional `starter`, `maps`, `resolutions` and initial `plugin_configs`. Pack planning and packed creation accept the same initial configuration. Its durable operation captures the installing admin and freezes the complete prepared schema, configuration and reviewed resource revisions. Each batch performs the configured `pack_steps_per_run` steps (20 by default), checks the enclosing deadline and rechecks live board ADMIN before each resource effect. The ordinary schema commit records `{id, version, digest, base}` provenance on `work.schema.applied`; subsequent resource and starter steps resume from recorded progress using stable resource ids and command keys. Automations use the platform's selected installation API under that admin's captured identity. Managed automation reconfiguration passes its reviewed `expected_revision` through Automation 0.2.27 or newer; a stale revision conflicts without changing the automation. Reviewed view revisions are enforced by the owning view API. Resource steps retain their platform ACLs, including parent WRITE for child creation and live source grants for automations. An exact `$board` input binds to the board id. Reusing the key with another request conflicts. `create` accepts `pack`, `version` and `starter`, with an optional declaration key prefix; an explicit `starter: false` opts out. Local schema changes retain provenance. Current and historical `get_schema` results include their committed `pack` and an `outdated` comparison with the installed entry. `kickside.work:packs.list({pack?})`, also `GET /work/packs/boards`, lists provenance only for boards administered by the caller.

Every declared field accepts an optional `title`, including computed and plugin fields. The declaration, compiled schema and `get_schema` retain it. Titles are nonblank text of at most 255 bytes; invalid titles return `field_title_blank` or `field_title_too_long` with kind `invalid`. A title-only edit plans and applies as `cosmetic` metadata: it records a generation immediately without migration, index or column work, queued rebuilds, or item changes. Historical generations keep their titles. For example, `{code = "assignee", title = "Assignee", type = "principal"}` names the displayed field while commands continue to use its code.

The `board_event_retention_days` requirement supplies the initial event retention policy, with a default of 90 days. Core stores each thread's effective policy in the database. The module has no UI declarations. Host requirements bind resources and security grants. Requirement metadata uses `value_kind` for registry resources and `value_type` for literals. The `registry_admin_grant` requirement declares `value_type: object` and accepts the host's structured `{ subject_id, subject_type, access_mask }` grant.

A change must pass `make verify` (setup, lint, typecheck, module checks and tests) and `make test-pg`. Use Wippy v0.3.59a or newer. Module checks require Node.js 20 or newer, Lua and Python 3 with the YAML parser installed. The alternate database harness uses port 5434 and database `kickside_test_work` by default.

Plugin manifests use `kickside.work.plugin`; field types use `kickside.work.type` and scopes `kickside.work.scope`. A board activates exact manifest IDs in `plugins: [{ use }]`. The `plugin_configs` map on create, plan and apply supplies initial attachment values outside the schema. Active configuration changes through `configure_plugin`. Board ADMIN admits `schema_options` independently of READ. A seam declares its manifest ID in `meta.plugin`; only an active plugin admits its types and scopes. `scopes` in the board schema records adopted scope IDs. Removing a plugin requires removing its schema references first. Deactivation cleans up the recorded projections and attachment even if the manifest was removed or the installed configuration stopped satisfying it. Component registers each attachment at the root and records the board as its owner in the same transaction. Board deletion uses that ownership to reap the attachment. Configuration checks live board ADMIN and the active board attachment association; a leased lifecycle job updates the attachment after the owning projection acknowledges its batch.

Manifests require `interface_version: 1`. The loader refuses a missing or unsupported version with `INVALID/plugin_interface_version_unsupported` before processing the manifest's declarations. Loaded manifests expose `interface_version` through `get_schema`, `schema_options` and `plugin_context`.

`schema_options.field_types` lists visible installed field types with their `id`, `title`, required `form`, optional allowed `indexes`, and optional `config_schema`. An omitted index list leaves index eligibility to the value form. Every field type allows `none`.

A manifest's `schema: { template }` or `schema: { provider }` (a `kickside.work:schema_provider` binding) contributes `fields`, `item_types`, `processes` and `relation_types`. Create, plan and apply resolve sources as the caller when the declaration includes `plugins`. Work stores each fragment, version and digest with that generation's declaration and event. Omitted `plugins` keeps those copies; configuration edits and receipt retries call no source. A fragment is bounded to 262144 canonical bytes and passes the declaration shape checks. An extension of a board-owned item type contains only `id` and appended `fields`; new types use full declarations. Colliding codes or ids fail with `plugin_schema_collision` and both owners. Compiled entries carry plugin provenance, and deactivation fails with `plugin_in_use` while surviving declarations reference a contribution. Indexed contributions use the normal layout diff and reindex job.

A plugin manifest declares `projections: [{ kind, input: "state" | "events", worker_ref: "func://<namespace>:<worker>", revision: 1 }]`; event input also declares `events`. Core invokes state workers in cursor-only mode. State workers call contract-only `plugin_feed { board_id, plugin, kind, token? }`, map its bounded, caller-authorized `changes`, store the returned opaque `token` in the body and acknowledge the triggering range only when `done` is true. Work owns paging, gap reset and bootstrap. Each page identifies its schema generation, and `reset` marks the first page after a gap, including gaps during an existing bootstrap. Event workers receive declared events directly and obtain their context from `plugin_context`. Work records desired state and enrolls its lifecycle job in the schema fold transaction. The job owns attachment creation and deletion and cursor registration at the causing event. The declared input selects the worker mode at registration. Effective configuration or revision changes reset the cursor; state input rebuilds from durable item pages. A worker fault parks only that cursor. Current plugin entries expose explicit `plugin`, `installed`, `active`, validated effective `config`, `lifecycle`, per-kind `projections` and structured `problem`. Historical generations omit live cursor state. Host `schema_options.plugins` supplies installed declarations and configuration schemas; `plugin_context` supplies active admission to plugin services. These methods add no agent tool.

Event projections can declare `start_seq`, a positive inclusive board event sequence used on registration and reset. Omission starts at the event that caused registration or reset. Bump the projection revision and resync to apply a changed declaration to an existing cursor. A request for pruned history fails registration with `CONFLICT/plugin_projection_gap` in `lifecycle.error`, which includes the earliest retained sequence as `floor`. Patch events require `schema_generation`, the board schema generation that encoded their numeric field IDs. Consumers can request that generation with `get_schema`.

Each generation retains its compiled snapshot and key prefix. Pinned items execute and list transitions from their recorded process generation. Discovery omits runnable edges whose settled state would increase occupancy beyond a hard WIP limit. Capacity uses all live occupants, including hidden items and regional states, while query counts follow caller visibility. `get_schema` includes each plugin's `plugin`, `version` and `digest` alongside its attachment state. `check_plugins: true` checks current sources as the caller and adds `outdated`; a failed source records a lifecycle error while the stored schema remains readable.

`kickside.work:view` creates, lists, reads, saves, renames, deletes and runs views. Save accepts an optional title and updates it with the definition in one component transaction. Rename and delete require the personal owner or board ADMIN; shared views are board-owned. Delete reports `deleted` or `in_progress` while component cleanup completes. Its component binding is `kickside.work.binding:view`, with class `kickside.work:view`. The board owns shared views placed beneath it. Personal views sit at root. View lists page in creation order over the views associated with that board and readable by the caller. Run uses the current viewer. Core initializes protected identity metadata on every user-created component; Work ignores it for view execution. Views use the shared query compiler for grouping, optional subgroups, and item pages. A grouped board query or saved-view run returns an exact group page when the visible candidate scan fits the read allowance. Use `group_limit` to set the page size from 1 to 200 (default 200) and pass `group_after` unchanged to continue with the same board, viewer, schema generation, grouping, and selection. The cursor follows indexed group keys with missing keys last. Two-level pages count subgroups toward the limit. A parent that spans pages repeats with its full count and measures. Each call reads a committed snapshot stamped with `as_of`. A bucket's `after` continues an item query filtered to that bucket, while a saved view's top-level `after` continues its flat item page. Single-board queries and views support up to three order keys with nulls last and keyset cursors. Cross-board queries reject grouped options with `INVALID/invalid_query`.

A saved view can set `view.boards` to up to 50 distinct board IDs or `"readable"`. The anchor board keeps the view’s placement, ownership and listing. Create and save validate compatible filters, columns, scopes and one sort key across the selection. Run uses the viewer’s live authority and the board query dispatcher. Pass `cross_after` to continue a cross-board view and restart without it when the selection, viewer authority or schema invalidates the cursor. Use `after`, grouping and `min_seq` with single-board views. Get and run require READ on the anchor and selected boards. When a selected board becomes inaccessible, get and run return a generic access denial and the anchor list returns only `view_id`, `board_id` and `status: "unavailable"` for that entry. List continuation advances through unavailable entries. Work resolves `"readable"` for the viewer at request time and stores only the selection expression.

Grouped queries and saved-view runs accept up to four `measures: [{ id, op: "sum", field }]` with unique ids. A measure requires board-wide READ on an indexed scalar `int` or `dec` field. Each bucket's `measures` maps ids to exact base-ten strings, including totals beyond JSON's safe integer range. Cleared and absent values contribute nothing. A measure with no values returns `null`. The same visible, filtered rows drive counts and sums. A read that is incomplete or waiting on an index rebuild omits the grouped result and its continuation.

A board is a component instance: its schema, plugins, plugin configuration and policy are data on that board and never affect another. App settings only supply defaults: board policy overrides the defaults declared under `kickside.work.settings`, and board plugin configuration overrides the plugin's settings namespace. Public meta publishes board title, description and icon, key prefix, generation, rebuild state, rebuild errors and `last_event_seq` on `component.<board_id>`. Clients use the notification to refetch `list_changes` from their cursor. Pass the returned cursor unchanged, including its opaque position when a page ends on a hidden row. Contract and agent tool pages and plugin feed tokens share the cursor schema. After a cross-board link or unlink commits, the destination's READ subscribers also receive `{ "event": "work.relations.invalidated" }` on its board topic. Clients refresh inbound relations with `list_links` under the reader's access. Queries wait only for rebuilding fields they actually use. `board_public_meta` grants the exact publisher the runtime meta capability on board components.

Time-in-state totals include every retained interval; detailed periods use an `after` continuation. Stored instants and history bounds use nine fractional UTC digits. PostgreSQL history predicates seek a bounded digest in the interval value index and compare the full stored canonical value for equality.

Links and comments use bounded pages with an `after` cursor. To guard a comment edit or delete, pass `expect_comment_version` from the corresponding comment read. An item defaults to at most 10,000 live comments, including additions within an atomic command; `comments_per_item` configures admission. Deleting a comment clears its body and mentions; its tombstone drains after the event replay window independently of item life. Unreadable link peers return `{ unavailable: true }` without identifiers. Board deletion follows the component service's DELETE gate. A board with placed children uses the platform's explicit `child_policy: reparent_root`; owned attachments remain linked to the board through lifecycle ownership.

`list_links` and `WorkListLinks` resume strictly after the last returned link in `(seq, board_id, from_id, type, to_board_id, to_id)` order. Reuse the opaque `after` string with the same board and selector. The deployment encryption key protects the position when an endpoint is unreadable. Each page reads current links. Removing a link at or before the boundary leaves the continuation valid, and new links at or before that boundary require a new traversal.

Schemas declare item visibility with `visibility: { field, levels: [{ id, holders }], bypass: admin }`. Holders name one exact `group`, `user`, `service` or principal `field`. Visibility fields use a single text or option value and an exact key index; compilation supplies a missing index. Rules permit at most 32 levels and 16 holders per list. Caller memberships resolve live through `kickside.contract:directory`, with a cap of 100 groups. Access conditions use bound parameters, capped at 4096. Native directory and named-scope failures retain their kind, details and retryability. A missing scope without a native error returns `UNAVAILABLE/access_group_missing`; malformed or unavailable authority answers use `UNAVAILABLE/contract_unavailable`. A hidden item returns the same result as a missing item, including key lookups and command references. Changing visibility schedules the existing reindex job and fences reads that depend on its indexes.

Fields declare `access: { read: [holders], write: [holders] }`. Point reads and result projections resolve field holders against the item. Query filters and order keys require a board-wide read holder; item-dependent grants continue to govern individual results. Parent and ancestor query keys on visibility boards require the bypass, so cursors and predicate results keep hidden parent identities private. Denied field use returns `PERMISSION_DENIED` with `details.code = field_denied` and the field name. History, intervals, change feeds and transition listings redact unreadable values. Caller patches enforce write access; declared transition effects retain the process's authority. Stored `when` predicates use caller visibility, while rollup predicates retain their caller-free evaluation. Relation and child predicates range over caller-visible peers. Host visibility can use protected holder fields within the access parameter bound. The caller's filter still obeys field READ, nesting, value and traversal limits.

On boards declaring visibility, rollup values and rollup filters require the declared ADMIN bypass. Field-based holders can grant different principals access within the same visibility level.

Item `get` and `WorkGetItem` return an optional `field_edit` map for the requested live item when the caller has board WRITE and the item carries declared fields. Each field code maps to `editable`, `field_denied`, or `read_only` using the same holder and computed or board-assigned field checks as direct `set`, `clear` and `unset` patches. Holder checks use the stored item snapshot, while `values` and `value_states` still follow field read access. A patch also has to satisfy version, value and process checks when submitted. The map is computed only for the requested item detail.

Item `get` resolves a key on the supplied board, including a retained move alias originating there. A board-scoped alias read requires READ on the source board and access to the destination item. An unrelated board returns `item_not_found` for that key. A contract or `WorkGetItem` call with no board uses the global key lookup. A board from trait context also scopes `WorkGetItem`, and the HTTP route supplies the board.

Change feeds charge up to `budget.rows` candidate rows and advance over rows omitted by selection or visibility. A feed cursor resumes in `(updated_seq, item_id)` order. When the last examined item is hidden, the cursor carries an authenticated, encrypted position. It uses the deployment encryption key and binds the position to the board, sequence, floor and access fingerprint. Durable visibility snapshots support identity-only deletes when an item leaves the reader's view. Feed cursors carry an access fingerprint that includes the rendered item key prefix. A nonzero continuation requires the returned fingerprint. A missing or changed fingerprint produces a gap and a restart cursor, including when the prefix, schema, live groups or the bypass changes. Visibility snapshots contain only the visibility field and its holder fields, survive audit-log expiry, and are removed with the board. Feed admission uses the higher of Core's durable event-prune boundary and Work's floor in the same read snapshot. The retention owner uses Core's boundary, visibility snapshot age and tombstone collection to advance Work's floor for compaction, which retains one baseline per item. Older cursors return a gap as soon as Core commits a higher boundary. Visibility age-floor discovery and cleanup limit candidates before checking timestamp or baseline eligibility and advance `(seq,item_id)` in the board's retention position. Both examined candidates and deletions count against the shared budget; surviving baselines and future snapshots advance the cursor without requesting endless idle continuation. A bootstrap cursor carries its admitted `floor`, so old live items can page through a fresh resync. Each feed upsert is one complete snapshot at its `updated_seq`, with up to 10,000 live comments. Feed comments expose only `comment_id`, `item_id`, `body`, `mentions`, `author`, `version`, `deleted`, `created_at` and optional `edited_at`; storage columns are not part of the snapshot. A response shares that 10,000-comment budget and defers the whole next item when necessary. Items above the snapshot cap carry `comments_truncated: true` and the first 10,000 comments in comment-id order; remaining data stays stored and is available through `list_comments`. Snapshots retain their document replacement/version contract when the marker is present. `list_comments` returns live comments in `(created_at, comment_id)` order and accepts the returned `after` string unchanged. Deleting a previously returned comment leaves the continuation valid.

`query` accepts `boards: [ids]` or `boards: "readable"`. The actor-scoped component listing selects work boards, with a cap of 50. Work admits compatible field forms on every selected board before spending the item allowance. A cross-board continuation applies to the admitted caller, schemas, filters and order. Each board applies its own visibility, field access, scopes and keyset cursor. Cross-board responses carry `board_id` on items, per-board `positions`, and a `cross_after` cursor for the next request. The total order is the requested value, board ID and item ID, with null values last. The merge shares one row allowance and deadline across board reads. A continuation carries per-board scan progress and the lower bounds needed to emit a sorted prefix. A page can be empty and carry `cross_after` while the merge establishes those bounds. Each call fetches at most 50 × 201 candidate and lookahead keys and renders at most 10,000 item documents. `kickside.work.read:select` compiles one table set per board.

Commands require WRITE independently of READ and return mutation outcomes. Dependency failures carried by an outcome retain `error: {kind, message, retryable, details}` through receipts, tools and HTTP; sinks and process workers reconstruct that exact native condition. A position-only command boundary waits under the validated board execution identity; public read methods still require READ. Receipts bind to their originating principal and recheck current item visibility on replay. Keyed item writes retain their subject CAS; receipt claims compare one of 256 fixed command hash-shard subjects per board, without adding a board-head fence. Ordinary receipts and terminal operation identities expire under the effective event retention policy stored by Core for their board. An inherited Core window keeps its exact millisecond duration in Work's expiry checks and cleanup deadlines. Disabling that policy pauses their age expiry. Creation fingerprints and successful completion results survive board lifetime, and operation phase receipts remain protected until settlement, including interrupted moves with reservations. The retention owner pages age candidates before evaluating receipt, generation and visit protection. Every inspected candidate consumes budget, including retained rows; complete age/key continuations use one bounded position per unfinished board. Equal-age and later-age expression-index seeks are separately bounded on SQLite. Failed rebuild diagnostics clear in the same candidate pass; unresolved demand remains. Future deadlines come from one age-index seek per row class, without filtering protected rows: a conservative wake may find that its candidate remains protected. Whole-board alias cleanup uses the existing `(board_id,at,key)` order. An exhausted collector allowance performs no candidate query and requests a new allowance to discover completion. Prefix discovery limits candidates before checking board presence; its existing position records completion until the board pass finishes. The owner does not rescan a retained population to find a deadline or a deletable result. Audit and closed intervals default to 365 days; zero windows select that finite default. Past-visit approvals and stage runs expire after the audit window, preserving current root and regional visits. Failed local jobs expire from their failure timestamp after that window, except unresolved reindex/recompute demand: it gates read admission until successful convergence, while only its error diagnostics and failure timestamp age away. Purged-item intervals, associations and native advance slots drain in bounded pages before the item tombstone can disappear. An indexed pending-purge bit prevents repeated scans of completed purges. Cleanup uses eligibility-leading indexes and timestamp order, shares the configured callback budget (500 units by default) and requests continuation while backlog remains. Identical cursor saves modify no rows. Inspecting retained visibility candidates advances the board's saved position.

Core >=0.3.17 retires exact subject names after permanent fencing. The retention owner retires `i:<item_id>` after the native advance slot has drained, `c:<comment_id>` before removing deleted comments or comments of a purged item, and `<operation_kind>:<operation_id>` after terminal unreferenced operation slots/history have drained (currently `bulk` emits progress subjects). Item UUIDs, comment UUIDs and operation UUIDs never recur; stale positive subject expectations still conflict. Each request contains at most 100 names and runs outside a Work SQL write transaction. Pending item markers, comment rows and operation rows remain retry addresses until Core succeeds; an ambiguous response retries the same names. Board-wide rank and path facts retain their physical metadata population for historical replay; they carry no retired item-subject expectation. A private owner callback handles synchronous operation-key expiry without granting retirement authority to member scopes. Shared board/schema/rank/range/plugin subjects, reusable registry prefixes and command shards keep their versions.

Retention persists the board and orphan scan positions. A discovery lap captures the largest board ID when it starts and advances through bounded keyset pages. Each board stores its next eligibility deadline and any unfinished collection cursor. The projection records an immediate due time in its existing board checkpoint transaction, including when Core coalesces the wake with another continuation. Due boards are visited by due time and board ID ahead of discovery, which gets a turn when a due page consumes the visit allowance. After a discovery lap, unfinished boards get one callback for each discovery callback before the next lap. Collection and future eligibility use the same clock snapshot and retention windows. Idle board state, event policy, prune boundaries and eligibility are read in bounded pages with index seeks. Purge appends a trusted item event with the scanned subject version. Purge and move-out preserve only visibility and field-holder inputs needed to authorize retained history. Cascading delete/restore authorizes every affected descendant before committing any lifecycle event. Its fold removes the generated item row; excess set values drain through bounded collection pages. Audit rows and closed intervals expire in bounded pages; 0 selects the 365-day default for each window. Tombstone removal advances the feed floor in the same transaction. Old unreferenced generations, zero field counts, completed jobs and converged inactive plugins have bounded collection paths. Board deletion retains Core’s fence across cleanup pages and removes generated tables and the board shell after owned rows drain.

Work publishes event ports for every board output, pullable item and change sources, an item-key writable sink, public tools exposed as virtual Blocks by the platform, and three agent traits. Flow nodes use the exact `kickside.work.traits:*` tool id. Each adapter calls the board contract under the caller's identity. Item sources retain durable change cursors and retract records outside their declared filter. The sink updates existing item keys or immutable item ids through apply receipts; the source is a registered Work write-source resource requiring its exact write capability. Work does not declare state-wait Blocks, event-body port filters or external-id upserts.

Agent tools live in `kickside.work.traits`. Their aliases use `Work` followed by the tool name in PascalCase. Each tool calls one exact contract method, inherits its input schema and access rules, with `board_id` optional wherever trait context supplies it, and adds `success = true` to its answer. Supply `board_id` in the call or omit it to use trait context; a call argument takes precedence. Item reads accept `{id}` or `{key}`; item operations require an immutable id string returned by `WorkGetItem` or `WorkFindItems`. Resolve a key with `WorkGetItem` before writing. `WorkGetTimeInState` accepts its returned integer `after` cursor to continue interval pages. The board and tool schemas require 1 to 200 operations with a known string `op` for apply and bulk templates. The command pipeline reports board-dependent validation in per-operation outcomes. `WorkListLinks` and `board.list_links` require exactly one selector, `item` or `target`. Typed response maps retain object identity when empty; list responses remain arrays.

- `kickside.work.traits:work_readonly` reads: `list_boards`, `get_schema`, `find_items`, `get_item`, `count`, `explain`, `list_history`, `get_time_in_state`, `list_links`, `list_comments`, `list_changes`, `bulk_status`, `move_status`, `list_packs`, `list_views`, `get_view`, `run_view`.
- `kickside.work.traits:work` includes those reads and item/view writes: `apply`, `transition`, `comment`, `approve`, `report`, `bulk`, `cancel_bulk`, `create_view`, `save_view`, `rename_view`, `delete_view`.
- `kickside.work.traits:work_admin` pairs with `work` and includes structure/configuration tools: `create_board`, `update_board`, `plan_schema`, `apply_schema`, `pack_plan`, `pack_apply`, `configure_plugin`, `plan_move`, `move`, `resume_migration`; its reads are `list_boards`, `get_schema`, `list_packs`, `schema_options`, `list_pack_boards` and `move_status`. `move_status` requires source board WRITE and operation ownership or source board ADMIN. `schema_options` discovers installed plugins and their configuration schemas under board ADMIN; `resume_migration` resumes a parked follow migration under board ADMIN; `list_pack_boards` lists installed provenance only for boards administered by the caller.

`list_boards`, `create_board`, `update_board`, `find_items` and `get_item` call board `list`, `create`, `update`, `query` and `get`. `WorkTransition` and `WorkComment` call board `apply` with batches of their named operation. The wrappers reject a foreign operation before applying any part of the batch. Mixed batches use `WorkApply`. The view tools call `kickside.work:view` methods and `list_pack_boards` calls `kickside.work:packs.list`; the other tools call their matching `kickside.work:board` methods. Working and administration traits compile together with each tool exactly once. The exact union is declared by `kickside.work.security:work_tools`; ordinary module membership grants no tool discovery or invocation.

Before advancing after `WorkApply`, `WorkTransition`, `WorkComment`, `WorkApprove` or `WorkReport`, inspect each `outcomes[].status`, `rolled_back` and `findings[].code`. A call can return `success = true` with a conflict, denial, or rollback. The statuses are `applied`, `unchanged`, `conflict`, `invalid`, `denied` and `unavailable`. An atomic rollback marks the affected outcome `unchanged` with `rolled_back = true`.

Plugins declare optional `tools` ids on their existing plugin manifest. Declaration validation refuses missing or non-tool entries with `plugin_tool_invalid`; installed-plugin options and `get_schema.plugins[]` include these ids. Read and working traits use compiler build functions to contribute the active board's plugin tools through the caller's board contract; without board context they contribute installed declarations. The read trait contributes only tools whose required scopes are exactly `[state.read]`. Plugins own their handlers and exact `tool_access` policies and declare no traits. Inactive plugin contracts return `plugin_inactive`. The upstream MCP server expands static trait tools only, so compiler contributions do not appear through that static expansion.

Projection and provider seams stay outside the traits: `board.plugin_feed`, `board.plugin_context`, `schema_provider.resolve`, and `search_resolver.resolve_ids`. Schema answers describe the same supported process states as declarations, including automation, gates, awaited principals, timers and parallel regions.


Processes declare human, gate, automated and parallel states. Manual states may declare `awaiting` as `{ group }`, `{ field }` naming a principal field, or a list of `{ kind, id }` principals. Gates use `release_when.approvals.from` with the same vocabulary. `get` and change-feed upserts return `awaiting: { since, by?, can_act, principals? }` for declared states and approval gates; query pages request `include: [awaiting]`. `since` is the current state entry time and optional `by` is entry plus the state’s `due` duration. Eligibility includes live group memberships and gate `prevent_self`, and does not grant board WRITE. `{ awaiting: true }` is a filter-tree node for visible live items awaiting the caller, compiled to SQL before paging and counts. States without an awaited source omit the answer. Pinned items retain their recorded rule. `principals` returns the unexpanded source using the recorded process and stable field ids; cleared sources return an empty list, while retired or unreadable principal fields omit it. Feed upserts carry `visit` and `process_generation` for consumers that correlate work with a state visit. Gates combine approvals, waits and predicates; `approve` records decisions for an item visit. Item `get` and change-feed upserts expose `gate` with current approvals, the entrant and entry time, and `can_approve`; query items include it when requested with `include: [gate]`. Read eligibility and the approve command share the live principal/group and `prevent_self` rule. Automated entries publish stage facts and `report` records progress and outputs of at most 64 KB, applies retry backoff and takes the outcome transition. `kickside.work.traits:report` is available as a virtual tool Block. Timers use ordinary board-scoped deadline Jobs, eligible for native terminal retention. A timer’s absolute field deadline is validated on entry. Calendar dates resolve to UTC midnight, and accepted deadline years are 0001–9999. Trash suspends a visit’s deadlines. Restoration reuses an active Jobs enrollment for each outstanding root and regional timer, or enrolls it at its original deadline if the job settled in trash. Timer commands fence against the lifecycle and visit observed by the worker. Native settlement of a retained timer and the restore fold share the board projection lock. Permanently purged identities never enter migration, rebuild, reindex, recompute, schema validation, rank demand or bulk admission. Stale advance and timer jobs complete without appending work after retirement; migration ignores retained tombstones even when their Core subject version no longer exists. Change feeds may still emit identity-only deletes for retained tombstones, so consumers remove prior documents; such deletes admit no item mutation, timer, reference expansion or subject write. New visits create no retained timer slots. Work does not read native Jobs tables in production. Hard WIP limits use a board-head expectation, while soft limits return findings. WIP checks seek root and regional memberships among live items and stop counting once they can decide the limit. Schema admission seeks only affected states among live and trashed items and counts each item once per state. Follow migrations compose every intervening generation map; pinned items use their recorded definition through completion. Timer lookups, transition requirements, copy sources and effect destinations resolve through that generation’s stable field IDs. Predicate and effect admission apply the live field definitions and authority by stable field ID. A custom predicate retains its binding when its live field code collides with an item property. Reusing a field code for a different ID advances the generation of each process that refers to it. `resume_migration` resumes Work’s parked migration job; reactivating a disabled execution subject can also require separate repair of Core’s invalid projection declaration.

Field forms remain immutable for an existing field id, including after its values disappear. Documents keep explicit absent, cleared and provided states; reads expose them in `value_states`, and indexed fields support `is_state`. Numeric option indexes retain separate identity and order values. Equality, grouping and history use the option id, while ranges and sorting use order. Changing an indexed numeric option order is a semantic schema edit. A label-only edit is cosmetic.

Work supports item references, rank fields, formulas and rich text through its existing forms. Item references resolve as the caller and redact inaccessible targets in read results. Rank fields and live item change-feed upserts expose the system rank. An optional `expect_version` on a rank command checks the item version in the committing snapshot. Rank changes keep the item edit version. Formulas declare an `expression` and result form, persist failed-result findings, evaluate dependencies on the command working document, and backfill through recompute jobs when the formula or the item types carrying it change. Formula-index queries wait for pending recomputation. Rich text declares `config.format: json` and stores complete document replacements. History supports `changed`, `from` and `to`; interval-based `was` queries preserve period authors after audit retention. Queries support direct-children quantifiers and `include: [transitions]` for batched transition availability. Indexed principal fields support `member_of` with a group id or list in queries, views, transition conditions and gate release conditions; membership resolves through the public security directory.

Plugin manifests declare required plugins and exact seam IDs. Activated `kickside.work.guard` functions run for transition commands against the proposed item values and for listings against the current values; state invariants persist findings, including explicit outage findings. `kickside.work.operand` functions resolve bounded concrete values as the caller. Adopted search scopes declare folded text `match` columns or a `kickside.work:search_resolver` binding. A scope backed by a plugin projection declares its owning plugin's projection kind in `meta.projection`. Reads that use the scope with `min_seq` return retryable `projection_pending` while its cursor's `last_seq` is below that sequence. A plugin with one search row per board and item passes its transaction and original text to `kickside.work.read:scopes.write_search`. Work folds the declared text columns before inserting or replacing the row. Plugins that own a different write shape call `kickside.work.domain:search_text.fold` on each search column at write time. Work folds SQL-scope operands with the same Unicode 17 default full case folding and matches a literal substring. Accents and combining marks retain their original form. Resolver bindings receive the original query. Their declared `meta.reads` fields must be board-public and may use `index: none`. A resolver runs as the caller before the item read transaction. Work verifies the captured projection position before applying candidate membership and its ordinary query and visibility rules.

Plugin callbacks can import `GuardRequest`, `GuardResult`, `OperandRequest` and `OperandResult` from `kickside.work:types`. A guard returns `allow` and a list of findings. An operand returns a concrete value directly.

Reads default to a two-second budget, configured by `read_deadline_ms`. PostgreSQL snapshot `statement_timeout` uses the remaining effective deadline in whole milliseconds; a caller deadline can shorten the setting, and an exhausted budget fails before enabling a timeout. PostgreSQL reserves zero for disabling that timeout, so an allowance below one whole millisecond returns `TIMEOUT` instead. Already exhausted query/count requests return their admitted empty incomplete result before opening a data snapshot. Single-board pages contain at most 200 items; cross-board queries include at most 50 boards and grouped queries return at most 200 lanes per group page. Generated text keys use binary order on both engines. Indexed text prefixes seek a literal key range, and positive set membership starts from the matching IDs. Index-only pages charge matching candidates. Residual predicates, including graph predicates, substring filters and SQL-scope match, evaluate after the ordered candidate window is bounded. A page charges the candidates it inspected and may return an empty page with a continuation. Cross-board item-reference sorting orders visible targets by their keys and treats unavailable targets as nulls. It uses indexed walks for the key and null passes and protects private seek positions in the continuation. Continue bounded reads using the cursor returned by each method.

Query-driven `bulk` freezes the matching item ids in one admitted snapshot and runs independent apply commands under the captured caller's live authority. Admission uses the bounded filtered query over live items, with optional trashed items. It freezes up to 200,000 matches and refuses a query with `INVALID/bulk_selection_limit` if the bounded scan cannot establish a complete selection. Indexed filters can select items from larger boards. Residual predicates charge examined candidates to the same limit. Durable owner records retain the identity, frozen page keys and progress; Core jobs carry only a locator. Pages default to 200 items and at most 200 apply operations, with smaller item chunks when a template contains several operations. Settings `bulk_batch_items` and `bulk_batch_ops` tune these independently; a template larger than `bulk_batch_ops` returns `INVALID/bulk_template_limit`. Each page commits its item endpoint and apply-chunk size in the existing operation data before effects. Recovery reuses those boundaries and receipt keys when either batching setting changes; later pages use the new settings. A template exceeding a newly started page’s apply limit returns `INVALID/bulk_template_limit`; an interrupted frozen page finishes under its recorded limit. `bulk_status` reports completed items and operation outcomes; `cancel_bulk` finishes an executing page, keeps committed work, and prevents later pages. Changing batches publish progress, including cancelled state when cancellation occurs during execution. Unchanged intermediate batches persist the operation cursor and counts. Every successful bulk operation retains its `finishing` boundary until its keyed terminal progress fact commits, even when the final batch changes no items or the selection is empty. Native Jobs still persists scheduling and lease state for restart and resume.

`plan_move` requires source WRITE and DELETE plus target WRITE and validates type, state, field and relation mappings without changing either board. Explicitly dropped fields require no source read. `move` reserves the live, visible source subtree, imports mapped items and links on the target, and finalizes source tombstones through its durable job. Item types select `move_children: move` or `refuse`. Receipts keep phase retries idempotent. If the source advances before prepare, `move` cancels the parked job, records the attempt as failed, releases its key and returns a `head_mismatch` conflict. A subsequent request with that key plans against the current source. Trashed descendants stay on the source. Source tombstones clear value payload and process working data while retaining authorization inputs; source relation aggregates recompute as endpoints move. Source keys follow aliases to the final destination under live destination access; aliases expire with source tombstones. `move_status` reports the durable operation and only readable target ids. Move plans and both move-history forms redact inaccessible peers through the shared peer redactor. Deferred execution rechecks every source item and each mapped noncomputed field, including cleared fields, under the captured operation identity and its live group memberships before importing data. Field-only revocation refuses the move before target import. Repeating an already prepared move's key after restoring its authority resumes the same frozen job.

Automated states may declare `run.flow_ref: { kind: flow, id, version }`; `run.stage` remains a label. The reference names one exact published version. Compilation rejects malformed references and unknown reference fields. Schema plan/apply, including pack preparation and frozen pack execution, require board ADMIN, Flow READ for both the schema caller and the board's stored execution principal, and a Start schema that accepts the fixed Work envelope `board_id, item, state, visit, attempt`. No input mapping is supported. Planning creates no launcher. Apply calls the selected Sync installer before appending a bound schema, with one deterministic board-child ID and constant configuration. Installer refusals leave the schema unapplied; schema conflicts reuse the same install request. The board service’s `delete` method verifies the owned launcher’s identity, parent and constant configuration, requests its removal, and returns typed retryable `stage_launcher_delete_pending` until that child disappears; it then requests board deletion. Core refuses direct board deletion while live children remain. Teardown is a lifecycle contract method without an agent tool or HTTP endpoint. Unbound declarations do not provision or reconfigure a launcher.

Initial and retry `stage.entered` events for bound states freeze that reference and the complete Work envelope. Unbound stages emit stage events without a Flow reference. Pinned processes retain their recorded reference on retry; future items use the new binding. Rebinding requires stopping new entries, draining existing attempts and deliveries, pausing the launcher, saving bindings, then resuming entries. Historical entries are not backfilled. Idle bindings do not pin Flows against deletion; schema admission rechecks availability.

The owned launcher consumes new entries independently of board reports and timers. Its adapter resolves the attempt by the owned board, item, visit and attempt. The adapter waits for the Work projection to reach the committed head before acknowledging an unbound or obsolete entry. Delivery stays retryable while the projection is behind or its unfinished visit is retained in trash. Automation redelivers the same attempt after restore. A current attempt launches only if its projected entry has a frozen Flow binding. The adapter passes only `board_id,item,state,visit,attempt` to that Flow, and hashes `(board,item,visit,attempt)` as its downstream idempotency key across delivery generations. It validates the owned Automation identity in the execution frame and preserves that delivery’s Automation origin and reference. The stage entry fold stores the exact Flow version and state with the current attempt. A follow migration can update the item’s process generation while the entered envelope stays fixed. Capacity and provider errors remain retryable. A definite refusal with no existing reservation finishes the attempt as `failed` with `outputs.error = flow_launch_rejected`; a reservation after ambiguous admission remains pending for Workflows recovery and completion.

The board implements Workflows’ typed `run_completion.complete` contract. Work validates its exact board/item UUID token and positive integer visit/attempt, requires live board WRITE and the stored board principal, and never switches a caller’s principal. Within the existing item CAS, it requires a current root/regional unfinished attempt and reuses the report finisher: `completed → passed`, `cancelled → canceled`, `failed/terminated → failed`. A committed report wins. Duplicate, stale, retired and missing attempts acknowledge without appending. Retry/backoff and outcome transitions use the same finisher as reports. A callback for a retained visit records its terminal outcome in trash without taking an outcome transition. Restore resumes any recorded retry deadline. Outputs and progress remain on `report`; silent successful runs now close successfully. Timeouts guard runs that never terminate. No failure-consumer port or companion Automation is required.

Known: a concurrent state exit can race the adapter’s admission read; the launched run’s completion is fenced against the newer visit. Concurrent first-time installers can conflict and retry. Principal changes require a new authenticated session; requests under another user principal are refused up front. No additional state, lock or recovery mechanism is added for these cases.

Work declares Workflows, Sync and Automation dependencies as `*` in `src/_index.yaml`; the harness locks select their published releases, including Workflows completion #524, pending-completion deletion protection #512, Sync prepared installation #521 and rooted selected installation #528. Run `make setup` to install the committed harness lock, or `make lockrefresh` to refresh it from the Hub. Local platform source replacements are excluded from repository configuration.

Explicit stage outcome routes and timer transitions must name a non-automatic transition whose source includes the holding state or is `any`. Transition copies between reference fields require the same declared target kind. Transition listings for people omit automatic transitions and transitions named only as `run.on_pass`, `on_fail`, `on_cancel` or `on_exhausted` targets. A transition declares `people: true` to offer such an action explicitly; `people: false` hides an ordinary exit. Point reads and awaiting query pages use the same Work rule and the recorded process generation.

Automatic default edges are considered after the other automatic edges and must pass their own `when` predicate and guards. Process commands validate references in transition patches against the live targets available to the caller. When a transition leaves a stage or parallel state, Work closes each unfinished attempt in the departing visits as canceled before recording the exit. Attempts that already finished retain their outcomes.

The stage visit limit applies at entry. An admitted visit uses `run.retry.max` to count attempts, with each eligible retry due at the failed attempt's finish time plus backoff. A terminal report, terminal Flow completion or stage timeout records the attempt outcome even when Work refuses the outcome transition. A public report returns `applied` with any routing findings in `outcomes[].findings` when the attempt is recorded. An eligible gate rejection similarly records the reviewer's decision when its reject route fails. Work admits route references under live access using the item's recorded definition and uses the same item CAS for the decision and any admitted transition. Named transitions and follow migrations cancel unfinished attempts before replacing their root or regional visits. Each keyed atomic command stores one receipt at the end of its append, so reports and approvals replay their original outcomes and final committed sequence after the item leaves the visit.

Sink configuration names an exact registered `kickside.work.write_source` resource. Its caller requires `work.source.write` and declaration discovery on that resource as well as the board's ordinary read/write authority. Fleet reads accept `limit` (at most 50) and `after`, and return a `next` continuation.

- `command_deadline_ms`: default 5000, inclusive range 1–60000.
- `read_deadline_ms`: default 2000, inclusive range 1–60000.
- `retention_batch`: default 500, inclusive range 205–5000.
- `bulk_batch_items`: default 200, inclusive range 1–2000.
- `bulk_batch_ops`: default 200, inclusive range 1–200.
- `rebuild_batch`: default 500, inclusive range 1–500.
- `rebuild_batches_per_run`: default 20, inclusive range 1–100.
- `migration_batch`: default 500, inclusive range 1–500.
- `migration_batches_per_run`: default 20, inclusive range 1–100.
- `rebalance_batch`: default 500, inclusive range 1–500.
- `rebalance_batches_per_run`: default 20, inclusive range 1–100.

A board may override `comments_per_item` in its policy. Deadlines and job/retention throughput are application settings; caller and job deadlines can shorten them. The retention minimum reserves enough units for native slot draining. Invalid values fail validation before a setting commit or schema admission. All retention day windows are integers in 0–106751, the largest whole-day duration representable in signed 64-bit nanoseconds; positive ISO durations share that upper bound and must represent at least one nanosecond. Positive subnanosecond durations return native `INVALID`, including signed/zero-enabled parsing; repeating timers therefore always advance. Parsing validates before integer multiplication. Audit and interval zero values still select 365 days. Every WIP policy key must name a state in the compiled processes; state removal must update its WIP policy in the same declaration.

The initial schema provides `(board_id,item_id,comment_id)` for purged-item comment cleanup, includes the deleted-comment age index with its comment ID tie-breaker, and provides the incoming relation index `(to_board_id,to_id,board_id,from_id,type)`. Board teardown drains incoming relations from other boards using complete keys in the same 100-row budget before removing the board shell. Both selectors have indexes matching eligibility and order.

Known platform gap: Settings 0.3.8 publishes committed revisions through `kickside.settings:settings_changes`, but Core 0.3.17 retention does not subscribe and Settings exposes no committed-change callback hook. Changing retention settings alone therefore does not re-arm an idle retention service. Work reads committed values on its next owner invocation. The platform must connect committed settings revisions to the existing Core retention notifier; Work adds no watcher or write-path notification.

Indexed lists keep the original order and repeated values in the item document. The generated membership table stores one row per distinct indexed key. Rebuild/reindex and rebalance event replay use fixed 500-item protocol bounds, independently of current execution batch settings. The initial schema includes every cleanup tie-breaker in receipt, alias, audit, interval, generation and terminal-operation age indexes. Generation protection uses positive live/trashed item and pending/running job-state seeks per bounded candidate, so the query skips retained rows when the active population is empty. Approval, stage-run, failed-job, item-life, visibility and comment selectors retain their matching complete indexes.

The functional test harness explicitly configures read and command budgets to 60000 ms: data and fixture assertions do not impose a production latency target on shared runners. Deadline tests choose their own setting or earlier caller deadline. The snapshot budget probe advances a clock through the existing deadline imports, checks expiry after snapshot work, and restores the real clock before returning; it never sleeps to reach a read deadline. Production defaults remain 2000 ms for reads and 5000 ms for commands.

### Task templates and recurring creation

Declare `kickside.work.templates:plugin` on a board to enable its versioned create presets. Use `kickside.work.templates:templates` to list, publish, archive, or instantiate a version. The Work trait contributes the corresponding tools on active boards. Board ADMIN publishes and archives versions. Board READ lists active versions, with default values limited by current field and item visibility. Board WRITE instantiates an exact version with an explicit key. Overrides replace only the declared field codes. The standard create command enforces current field access, parent visibility, entry requirements and workflow effects.

The catalog retains up to 128 versions per board. Archive hides a version from listing and refuses fresh creates. Existing keyed Work receipts replay while their evidence is retained. A version whose field identity changed needs a new publication and pin. The attachment emits publish and archive facts and removes the catalog on teardown.

Install `kickside.automation.recurring:task` through Automation's standard installation and pass the board ID as the parent. Placement requires board WRITE. The target below pins a template version and supplies an override.

```yaml
kind: action
port: kickside.work.templates:recurring
config:
  board_id: <work-board-id>
  template_id: <template-id>
  version: <exact-version-from-publish>
input:
  overrides:
    title: Weekly review
```

The task runs as its installer. Each occurrence checks the installer's current Work WRITE and create permissions. Work board event retention must cover Automation delivery and history retention. Automation reserves each send before attempting it. Operator replays use the same occurrence key and recover an existing Work receipt. When receipt evidence is unavailable, replay returns `template_replay_unavailable`.

To delete a board, delete or move its recurring tasks first. Component returns `CONFLICT` while a live recurring task is still placed under the board. [Work Templates specification](docs/SPEC.md)
