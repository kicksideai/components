# kickside/work

Work tracking on KickSide threads: boards of typed items, process transitions, hierarchy, relations, comments, rank and rollups. Each board owns a component, its event log and a projected read model.

Call `kickside.work:board` through the default service binding. HTTP handlers expose the same service under `/work/boards`. Component ACLs gate each operation; private producer policies reserve durable facts for validated commands and jobs.

- `kickside.work.domain`: schema, process, value forms, filter tree, predicates, layout, plugin manifests, rank and rollups.
- `kickside.work.persist`: repositories, generated tables, bulk writes, the threads client and event projection.
- `kickside.work.command`: prepare, apply, schema commands, query-driven bulk, cross-board moves and board creation.
- `kickside.work.read`: item, query compiler, scopes, history and changes views.
- `kickside.work.service`: validated contract boundary.
- `kickside.work.jobs`: migration, rank rebalance, rollup recompute, index rebuild, state timers, cross-item advance, captured-caller bulk and move completion.
- `kickside.work.retention`: bounded trash purge, age retention, teardown continuation and orphan prefix release.

One initial migration creates the current schema on SQLite and PostgreSQL.

The host supplies the database, authenticated API router and prefix-registry administrator grant. Board creation requires the Work administration capability. The board kind is closed on Component 0.3.20 or newer. Exact create/update grants belong to Work's creation, pack execution and public metadata frames. Generic registration and context/meta mutation outside Work admission are refused. Ordinary Component access governs board placement, ancestor relocation and folder deletion with `reparent_root`. Component registration atomically stores a durable creation fingerprint with the board; failed admission creates no Work receipt. Retries compare that fingerprint independently of editable title and placement. Successful initialization stores its result beside the fingerprint; identical retries return that result without replaying the declaration, even after ordinary receipts expire. A fingerprint without a completion result denotes interrupted initialization, which resumes through the keyed schema or pack operation. Schema apply requires the registry grant when claiming a prefix.

`list({limit?, after?})` returns at most 50 boards and a `next` continuation. Pass `next` as `after` to continue through HTTP or `WorkListBoards`. Counts use caller-visible items and the same visibility-index rebuild fence as queries; public component metadata contains no population counts.

A successful `create` always establishes an initial schema generation. Omitting `declaration` creates an empty declaration with prefix `W` followed by the first nine hexadecimal characters of the deterministic board ID, uppercased; the ordinary prefix claim still detects conflicts. Existing schemaless boards and interrupted initializations can apply their first declaration at expected generation 0.

The board contract exposes `create`, `update`, `list`, `get_schema`, `plan_schema`, `apply_schema`, `list_packs`, `pack_plan`, `pack_apply`, `resume_migration`, `apply`, `approve`, `report`, `query`, `count`, `get`, `list_changes`, `list_history` `get_time_in_state`, `list_links`, `list_comments`, `explain`, `configure_plugin`, `bulk`, `bulk_status`, `cancel_bulk`, `plan_move`, `move` and `move_status`. Board list entries and item get/explain results include independent `access: {read, write, admin}` booleans for the caller. Explain includes the database planner’s selected index names and `budget: {rows_scanned, rows_remaining, deadline_remaining_ms}`; it plans without scanning item rows. Each HTTP operation owns a handler and endpoint entry. Shared model types live at `kickside.work:types`.

Reads return committed snapshots. A `min_seq` beyond the snapshot returns a retryable `UNAVAILABLE` error with code `projection_pending`. Deferred workers resolve the stored board identity and bound projection waits by the enclosing job deadline. Retention reports each blocked prefix and continues processing the batch.

`update({board_id, title?, description?, icon?})` edits component metadata under board ADMIN, independently of READ or WRITE. Omitted values stay; empty descriptions and icons clear those properties. Titles are nonblank text of at most 255 bytes. Supplying `key_prefix` returns `invalid` with `prefix_immutable`. The result reports `status: updated` or `status: unchanged`; unchanged requests append no event. Each edit records `kickside.work.events:board.updated`, whose closed schema binds `output_kind` to the board binding, and exposes `kickside.work.ports:board_updated`. The board projection and public meta publisher retain these edits before and after the first schema. Board list entries and item get results include board title, description and icon. HTTP uses `POST /work/boards/{id}/update` under the administration endpoint policy.

Packs are caller-visible `registry.entry` declarations with `meta.type: kickside.work.pack` and title, version, icon and description metadata. Their data contains `schema`, optional `processes`, shared `views`, `automations`, `traits`, `starter: {items, default}` and `requires` naming exact plugin manifests. `GET /work/packs` lists their canonical data digests and whether each required plugin is available under the caller's scope. Invalid declarations remain identifiable entries with a structured `problem` and cannot install. Pack modules grant their exact entry ids; Work grants no wildcard access to external declarations. Registry declarations canonicalize integral numbers at their read boundary before strict declaration validation. Pack digests and outdated checks use that same representation; fractional counts retain their condition errors.

`pack_plan({board_id, pack, version?, expected_generation})` requires board ADMIN and plans an install on an empty unprovenanced board or a three-way upgrade from its stored pack base. It returns ordinary schema classifications and migration paths, local conflicts, proposed state maps, shared views, automations, traits and plugin activations. Apply requires an explicit `maps` decision for state removals and `resolutions[path]: local | incoming` for conflicts. Missing plugins return `unknown_plugin`; another installed version returns `pack_version_unavailable`. Managed resource removal requires the plan's migration path.

`pack_apply` adds `key` and optional `starter`, `maps`, `resolutions` and initial `plugin_configs`. Pack planning and packed creation accept the same initial configuration. Its durable operation captures the installing admin and freezes the complete prepared schema, configuration and reviewed resource revisions. Each batch performs the configured `pack_steps_per_run` steps (20 by default), checks the enclosing deadline and rechecks live board ADMIN before each resource effect. The ordinary schema commit records `{id, version, digest, base}` provenance on `work.schema.applied`; subsequent resource and starter steps resume from recorded progress using stable resource ids and command keys. Automations use the platform's selected installation API under that admin's captured identity. Managed automation reconfiguration passes its reviewed `expected_revision` through Automation 0.2.27 or newer; a stale revision conflicts without changing the automation. Reviewed view revisions are enforced by the owning view API. Resource steps retain their platform ACLs, including parent WRITE for child creation and live source grants for automations. An exact `$board` input binds to the board id. Reusing the key with another request conflicts. `create` accepts `pack`, `version` and `starter`, with an optional declaration key prefix; an explicit `starter: false` opts out. Local schema changes retain provenance. Current and historical `get_schema` results include their committed `pack` and an `outdated` comparison with the installed entry. `kickside.work:packs.list({pack?})`, also `GET /work/packs/boards`, lists provenance only for boards administered by the caller.

Every declared field accepts an optional `title`, including computed and plugin fields. The declaration, compiled schema and `get_schema` retain it. Titles are nonblank text of at most 255 bytes; invalid titles return `field_title_blank` or `field_title_too_long` with kind `invalid`. A title-only edit plans and applies as `cosmetic` metadata: it records a generation immediately without migration, index or column work, queued rebuilds, or item changes. Historical generations keep their titles. For example, `{code = "assignee", title = "Assignee", type = "principal"}` names the displayed field while commands continue to use its code.

The `board_event_retention_days` requirement supplies the initial event retention policy, with a default of 90 days. Core stores each thread's effective policy in the database. The module has no UI declarations. Host requirements bind resources and security grants.

A change must pass `make verify` (setup, lint, typecheck, module checks and tests) and `make test-pg`. Use Wippy v0.3.59a or newer. Module checks require Node.js 20 or newer, Lua and Python 3 with the YAML parser installed. The alternate database harness uses port 5434 and database `kickside_test_work` by default.

Plugin manifests use `kickside.work.plugin`; field types use `kickside.work.type` and scopes `kickside.work.scope`. A board activates exact manifest IDs in `plugins: [{ use }]`. The `plugin_configs` map on create, plan and apply supplies initial attachment values outside the schema. Active configuration changes through `configure_plugin`. A seam declares its manifest ID in `meta.plugin`; only an active plugin admits its types and scopes. `scopes` in the board schema records adopted scope IDs. Removing a plugin requires removing its schema references first. Attachments remain unplaced and carry `owner` equal to the board ID for lifecycle reaping. Configuration checks live board ADMIN and the active board attachment association; a leased lifecycle job updates the attachment after the owning projection acknowledges its batch.

A manifest's `schema: { template }` or `schema: { provider }` (a `kickside.work:schema_provider` binding) contributes `fields`, `item_types`, `processes` and `relation_types`. Create, plan and apply resolve sources as the caller when the declaration includes `plugins`. Work stores each fragment, version and digest with that generation's declaration and event. Omitted `plugins` keeps those copies; configuration edits and receipt retries call no source. A fragment is bounded to 262144 canonical bytes and passes the declaration shape checks. An extension of a board-owned item type contains only `id` and appended `fields`; new types use full declarations. Colliding codes or ids fail with `plugin_schema_collision` and both owners. Compiled entries carry plugin provenance, and deactivation fails with `plugin_in_use` while surviving declarations reference a contribution. Indexed contributions use the normal layout diff and reindex job.

A plugin manifest declares `projections: [{ kind, input: "state" | "events", worker_ref: "func://<namespace>:<worker>", revision: 1 }]`; event input also declares `events`. Core invokes each declared worker directly with its native projection input. State workers call contract-only `plugin_feed { board_id, plugin, kind, token? }`, map its bounded `changes`, store the returned opaque `token` in the body and acknowledge the triggering range only when `done` is true. Work owns paging, gap reset and bootstrap. Event workers receive declared events directly and obtain their context from `plugin_context`. Work records desired state and enrolls its lifecycle job in the schema fold transaction. The job owns attachment creation and deletion and cursor registration at the causing event. Effective configuration or revision changes reset the cursor; state input rebuilds from durable item pages. A worker fault parks only that cursor. Current plugin entries expose explicit `plugin`, `installed`, `active`, validated effective `config`, `lifecycle`, per-kind `projections` and structured `problem`. Historical generations omit live cursor state. Host `schema_options.plugins` supplies installed declarations and configuration schemas; `plugin_context` supplies active admission to plugin services. These methods add no agent tool.

Each generation retains its compiled snapshot and key prefix. Pinned items execute and list transitions from their recorded process generation. `get_schema` includes each plugin's `plugin`, `version` and `digest` alongside its attachment state. `check_plugins: true` checks current sources as the caller and adds `outdated`; a failed source records a lifecycle error while the stored schema remains readable.

`kickside.work:view` creates, lists, reads, saves, renames, deletes and runs views. Save accepts an optional title and updates it with the definition in one component transaction. Rename and delete require the personal owner or board ADMIN; shared views are board-owned. Delete reports `deleted` or `in_progress` while component cleanup completes. Its component binding is `kickside.work.binding:view`, with class `kickside.work:view`. The board owns shared views placed beneath it; personal views sit at root. Run uses the current viewer. Core initializes protected identity metadata on every user-created component; Work ignores it for view execution. Views use the shared query compiler for grouping, optional subgroups, complete group counts and a first page per group. Single-board queries and views support up to three order keys with nulls last and keyset cursors. A grouped response holds at most 200 groups.

A board is a component instance: its schema, plugins, plugin configuration and policy are data on that board and never affect another. App settings only supply defaults: board policy overrides the defaults declared under `kickside.work.settings`, and board plugin configuration overrides the plugin's settings namespace. Public meta publishes board title, description and icon, key prefix, generation, rebuild state, rebuild errors and `last_event_seq` on `component.<board_id>`. Clients use the notification to refetch `list_changes` from their cursor. Queries wait only for rebuilding fields they actually use. `board_public_meta` grants the exact publisher the runtime meta capability on board components.

Time-in-state totals include every retained interval; detailed periods use an `after` continuation. Stored instants and history bounds use nine fractional UTC digits.

Links and comments use bounded pages with an `after` cursor. An item defaults to at most 10,000 live comments, including additions within an atomic command; `comments_per_item` configures admission. Deleting a comment clears its body and mentions; its tombstone drains after the event replay window independently of item life. Unreadable link peers return `{ unavailable: true }` without identifiers. Board deletion follows the component service's DELETE gate. A board with placed children uses the platform's explicit `child_policy: reparent_root`; owned attachments remain linked to the board through lifecycle ownership.

Schemas declare item visibility with `visibility: { field, levels: [{ id, holders }], bypass: admin }`. Holders name one exact `group`, `user`, `service` or principal `field`. Visibility fields use a single text or option value and an exact key index; compilation supplies a missing index. Rules permit at most 32 levels and 16 holders per list. Caller memberships resolve live through `kickside.contract:directory`, with a cap of 100 groups. Access conditions use bound parameters, capped at 4096. Native directory and named-scope failures retain their kind, details and retryability. A missing scope without a native error returns `UNAVAILABLE/access_group_missing`; malformed or unavailable authority answers use `UNAVAILABLE/contract_unavailable`. A hidden item returns the same result as a missing item, including key lookups and command references. Changing visibility schedules the existing reindex job and fences reads that depend on its indexes.

Fields declare `access: { read: [holders], write: [holders] }`. Point reads and result projections resolve field holders against the item. Query filters and order keys require a board-wide read holder; item-dependent grants continue to govern individual results. Parent and ancestor query keys on visibility boards require the bypass, so cursors and predicate results keep hidden parent identities private. Denied field use returns `PERMISSION_DENIED` with `details.code = field_denied` and the field name. History, intervals, change feeds and transition listings redact unreadable values. Caller patches enforce write access; declared transition effects retain the process's authority. Stored `when` predicates use caller visibility, while rollup predicates retain their caller-free evaluation. Relation predicates include peer visibility; the filter tree's nesting and value limits also bound these expanded predicates.

On boards declaring visibility, rollup values and rollup filters require the declared ADMIN bypass. Field-based holders can grant different principals access within the same visibility level.

Change feeds advance over filtered rows. Durable visibility snapshots support identity-only deletes when an item leaves the reader's view. Feed cursors carry an access fingerprint; changes to schema, live groups or the bypass produce a gap and a restart cursor. Visibility snapshots contain only the visibility field and its holder fields, survive audit-log expiry, and are removed with the board. The event-retention age window advances the feed floor independently of item deletion. Older cursors return a gap; compaction retains one baseline per item at that floor. Both age-floor discovery and cleanup limit candidates before checking timestamp or baseline eligibility and advance `(seq,item_id)` in the existing retention position. Both examined candidates and deletions count against the shared budget; surviving baselines and future snapshots advance the cursor without requesting endless idle continuation. A bootstrap cursor carries its admitted `floor`, so old live items can page through a fresh resync. Each feed upsert is one complete snapshot at its `updated_seq`, with up to 10,000 live comments. Feed comments expose only `comment_id`, `item_id`, `body`, `mentions`, `author`, `version`, `deleted`, `created_at` and optional `edited_at`; storage columns are not part of the snapshot. A response shares that 10,000-comment budget and defers the whole next item when necessary. Items above the snapshot cap carry `comments_truncated: true` and the first 10,000 comments in comment-id order; remaining data stays stored and is available through `list_comments`. Snapshots retain their document replacement/version contract when the marker is present.

`query` accepts `boards: [ids]` or `boards: "readable"`. The actor-scoped component listing selects work boards, with a cap of 50. Used fields require compatible forms across boards. Each board applies its own visibility, field access, scopes and keyset cursor. Cross-board responses carry `board_id` on items, per-board `positions`, and a `cross_after` cursor for the next request. The total order is the requested value, board ID and item ID, with null values last. The merge fetches at most 50 × 201 index rows and loads at most 10,000 item documents; a database sort compares these bounded candidates using the engine's own ordering. Deadline checks between board reads use the configured read budget (two seconds by default). `kickside.work.read:select` compiles one table set per board.

Commands require WRITE independently of READ and return mutation outcomes. Dependency failures carried by an outcome retain `error: {kind, message, retryable, details}` through receipts, tools and HTTP; sinks and process workers reconstruct that exact native condition. A position-only command boundary waits under the validated board execution identity; public read methods still require READ. Receipts bind to their originating principal and recheck current item visibility on replay. Keyed item writes retain their subject CAS; receipt claims compare one of 256 fixed command hash-shard subjects per board, without adding a board-head fence. Ordinary receipts expire with the event window, creation fingerprints and successful completion results survive board lifetime, and operation phase receipts remain protected until settlement, including interrupted moves with reservations. The retention owner pages age candidates before evaluating receipt, generation and visit protection. Every inspected candidate consumes budget, including retained rows; complete age/key continuations reuse the existing `item_after` position. Equal-age and later-age expression-index seeks are separately bounded on SQLite. Failed rebuild diagnostics clear in the same candidate pass; unresolved demand remains. Future deadlines come from one age-index seek per row class, without filtering protected rows: a conservative wake may find that its candidate remains protected. Whole-board alias cleanup uses the existing `(board_id,at,key)` order. An exhausted collector allowance performs no candidate query and requests a new allowance to discover completion. Prefix discovery limits candidates before checking board presence; its existing position records completion until the board pass finishes. The owner does not rescan a retained population to find a deadline or a deletable result. Audit and closed intervals default to 365 days; zero windows select that finite default. Past-visit approvals and stage runs expire after the audit window, preserving current root and regional visits. Failed local jobs expire from their failure timestamp after that window, except unresolved reindex/recompute demand: it gates read admission until successful convergence, while only its error diagnostics and failure timestamp age away. Purged-item intervals, associations and native advance slots drain in bounded pages before the item tombstone can disappear. An indexed pending-purge bit prevents repeated scans of completed purges. Cleanup uses eligibility-leading indexes and timestamp order, shares the configured callback budget (500 units by default) and requests continuation while backlog remains. Identical cursor saves modify no rows; inspecting retained visibility candidates advances only the existing owner position.

Core >=0.3.17 retires exact subject names after permanent fencing. The retention owner retires `i:<item_id>` after the native advance slot has drained, `c:<comment_id>` before removing deleted comments or comments of a purged item, and `<operation_kind>:<operation_id>` after terminal unreferenced operation slots/history have drained (currently `bulk` emits progress subjects). Item UUIDs, comment UUIDs and operation UUIDs never recur; stale positive subject expectations still conflict. Each request contains at most 100 names and runs outside a Work SQL write transaction. Pending item markers, comment rows and operation rows remain retry addresses until Core succeeds; an ambiguous response retries the same names. Board-wide rank and path facts retain their physical metadata population for historical replay; they carry no retired item-subject expectation. Bulk admission counts only nonpurged items. A private owner callback handles synchronous operation-key expiry without granting retirement authority to member scopes. Shared board/schema/rank/range/plugin subjects, reusable registry prefixes and command shards keep their versions.

Retention persists both board and orphan scan positions. Purge appends a trusted item event with the scanned subject version. Purge and move-out preserve only visibility and field-holder inputs needed to authorize retained history. Cascading delete/restore authorizes every affected descendant before committing any lifecycle event. Its fold removes the generated item row; excess set values drain through bounded collection pages. Audit rows and closed intervals expire in bounded pages; 0 selects the 365-day default for each window. Tombstone removal advances the feed floor in the same transaction. Old unreferenced generations, zero field counts, completed jobs and converged inactive plugins have bounded collection paths. Board deletion retains Core’s fence across cleanup pages and removes generated tables and the board shell after owned rows drain.

Work publishes event ports for every board output, pullable item and change sources, an item-key writable sink, public tools exposed as virtual Blocks by the platform, and three agent traits. Flow nodes use the exact `kickside.work.traits:*` tool id. Each adapter calls the board contract under the caller's identity. Item sources retain durable change cursors and retract records outside their declared filter. The sink updates existing item keys or immutable item ids through apply receipts; the source is a registered Work write-source resource requiring its exact write capability. Work does not declare state-wait Blocks, event-body port filters or external-id upserts.

Agent tools live in `kickside.work.traits`. Their aliases use `Work` followed by the tool name in PascalCase. Each tool calls one exact contract method, inherits its input schema and access rules, with `board_id` optional wherever trait context supplies it, and adds `success = true` to its answer. Supply `board_id` in the call or omit it to use trait context; a call argument takes precedence. Item reads accept `{id}` or `{key}`; item operations require an immutable id string returned by `WorkGetItem` or `WorkFindItems`. Resolve a key with `WorkGetItem` before writing. `WorkGetTimeInState` accepts its returned integer `after` cursor to continue interval pages. Contract and tool input schemas carry the same descriptions; request-level value sets stay closed, and operation members judged by the command pipeline keep open schema types. Schema conformance checks nested descriptions and the full input schema, allowing only that context-supplied `board_id` difference. Typed response maps retain object identity when empty; list responses remain arrays.

- `kickside.work.traits:work_readonly` reads: `list_boards`, `get_schema`, `find_items`, `get_item`, `count`, `explain`, `list_history`, `get_time_in_state`, `list_links`, `list_comments`, `list_changes`, `bulk_status`, `move_status`, `list_packs`, `list_views`, `get_view`, `run_view`.
- `kickside.work.traits:work` includes those reads and item/view writes: `apply`, `transition`, `comment`, `approve`, `report`, `bulk`, `cancel_bulk`, `create_view`, `save_view`, `rename_view`, `delete_view`.
- `kickside.work.traits:work_admin` pairs with `work` and includes structure/configuration tools: `create_board`, `update_board`, `plan_schema`, `apply_schema`, `pack_plan`, `pack_apply`, `configure_plugin`, `plan_move`, `move`, `resume_migration`; its reads are `list_boards`, `get_schema`, `list_packs`, `schema_options` and `list_pack_boards`. `schema_options` discovers installed plugins and their configuration schemas under board ADMIN; `resume_migration` resumes a parked follow migration under board ADMIN; `list_pack_boards` lists installed provenance only for boards administered by the caller.

`list_boards`, `create_board`, `update_board`, `find_items` and `get_item` call board `list`, `create`, `update`, `query` and `get`. `transition` and `comment` are exact aliases of board `apply`. The view tools call `kickside.work:view` methods and `list_pack_boards` calls `kickside.work:packs.list`; the other tools call their matching `kickside.work:board` methods. Working and administration traits compile together with each tool exactly once. The exact union is declared by `kickside.work.security:work_tools`; ordinary module membership grants no tool discovery or invocation.

Plugins declare optional `tools` ids on their existing plugin manifest. Declaration validation refuses missing or non-tool entries with `plugin_tool_invalid`; installed-plugin options and `get_schema.plugins[]` include these ids. Read and working traits use compiler build functions to contribute the active board's plugin tools through the caller's board contract; without board context they contribute installed declarations. The read trait contributes only tools whose required scopes are exactly `[state.read]`. Plugins own their handlers and exact `tool_access` policies and declare no traits. Inactive plugin contracts return `plugin_inactive`. The upstream MCP server expands static trait tools only, so compiler contributions do not appear through that static expansion.

Projection and provider seams stay outside the traits: `board.plugin_feed`, `board.plugin_context`, `schema_provider.resolve`, and `search_resolver.resolve_ids`. Schema answers describe the same supported process states as declarations, including automation, gates, awaited principals, timers and parallel regions.


Processes declare human, gate, automated and parallel states. Manual states may declare `awaiting` as `{ group }`, `{ field }` naming a principal field, or a list of `{ kind, id }` principals. Gates use `release_when.approvals.from` with the same vocabulary. `get` and change-feed upserts return `awaiting: { since, by?, can_act, principals? }` for declared states and approval gates; query pages request `include: [awaiting]`. `since` is the current state entry time and optional `by` is entry plus the state’s `due` duration. Eligibility includes live group memberships and gate `prevent_self`, and does not grant board WRITE. `{ awaiting: true }` is a filter-tree node for visible live items awaiting the caller, compiled to SQL before paging and counts. States without an awaited source omit the answer. Pinned items retain their recorded rule. `principals` returns the unexpanded source using the recorded process and stable field ids; cleared sources return an empty list, while retired or unreadable principal fields omit it. Feed upserts carry `visit` and `process_generation` for consumers that correlate work with a state visit. Gates combine approvals, waits and predicates; `approve` records decisions for an item visit. Item `get` and change-feed upserts expose `gate` with current approvals, the entrant and entry time, and `can_approve`; query items include it when requested with `include: [gate]`. Read eligibility and the approve command share the live principal/group and `prevent_self` rule. Automated entries publish stage facts and `report` records progress and outputs of at most 64 KB, applies retry backoff and takes the outcome transition. `kickside.work.traits:report` is available as a virtual tool Block. Timers use ordinary board-scoped deadline Jobs, eligible for native terminal retention; stale visits do not change items. Permanently purged identities never enter migration, rebuild, reindex, recompute, schema validation, rank demand or bulk admission. Stale advance and timer jobs complete without appending work after retirement; migration ignores retained tombstones even when their Core subject version no longer exists. Change feeds may still emit identity-only deletes for retained tombstones, so consumers remove prior documents; such deletes admit no item mutation, timer, reference expansion or subject write. New visits create no retained timer slots. Work does not read native Jobs tables in production. Hard WIP limits use a board-head expectation, while soft limits return findings. Follow migrations compose every intervening generation map; pinned items use their recorded definition through completion.

Field forms remain immutable for an existing field id, including after its values disappear. Documents keep explicit absent, cleared and provided states; reads expose them in `value_states`, and indexed fields support `is_state`. Numeric option indexes retain separate identity and order values: equality, grouping and history use the option id, while ranges and sorting use order.

Work supports item references, rank fields, formulas and rich text through its existing forms. Item references resolve as the caller and redact inaccessible targets in read results. Rank fields expose the system rank. Formulas declare an `expression` and result form, persist failed-result findings, evaluate dependencies on the command working document, and backfill through recompute jobs when the formula or the item types carrying it change. Formula-index queries wait for pending recomputation. Rich text declares `config.format: json` and stores complete document replacements. History supports `changed`, `from` and `to`; interval-based `was` queries preserve period authors after audit retention. Queries support direct-children quantifiers and `include: [transitions]` for batched transition availability. Indexed principal fields support `member_of` with a group id or list in queries, views, transition conditions and gate release conditions; membership resolves through the public security directory.

Plugin manifests declare required plugins and exact seam IDs. Activated `kickside.work.guard` functions run for transition commands and listings; state invariants persist findings, including explicit outage findings. `kickside.work.operand` functions resolve bounded concrete values as the caller. Adopted search scopes declare text `match` columns or a `kickside.work:search_resolver` binding; search membership remains subject to the ordinary query and visibility rules.

Reads default to a two-second budget, configured by `read_deadline_ms`. PostgreSQL snapshot `statement_timeout` uses the remaining effective deadline in whole milliseconds; a caller deadline can shorten the setting, and an exhausted budget fails before enabling a timeout. PostgreSQL reserves zero for disabling that timeout, so an allowance below one whole millisecond returns `TIMEOUT` instead. Already exhausted query/count requests return their admitted empty incomplete result before opening a data snapshot. Single-board pages contain at most 200 items; cross-board queries include at most 50 boards and grouped queries return at most 200 groups. Continue bounded reads using the cursor returned by each method.

Query-driven `bulk` freezes the matching item ids in one admitted snapshot and runs independent apply commands under the captured caller's live authority. Durable owner records retain the identity, frozen page keys and progress; Core jobs carry only a locator. Pages default to 200 items and at most 200 apply operations, with smaller item chunks when a template contains several operations. Settings `bulk_batch_items` and `bulk_batch_ops` tune these independently; a template larger than `bulk_batch_ops` returns `INVALID/bulk_template_limit`. Each page commits its item endpoint and apply-chunk size in the existing operation data before effects. Recovery reuses those boundaries and receipt keys when either batching setting changes; later pages use the new settings. A template exceeding a newly started page’s apply limit returns `INVALID/bulk_template_limit`; an interrupted frozen page finishes under its recorded limit. `bulk_status` reports completed items and operation outcomes; `cancel_bulk` finishes an executing page, keeps committed work, and prevents later pages. Changing batches publish progress, including cancelled state when cancellation occurs during execution. A changing final batch retains its `finishing` boundary until its progress fact commits. Unchanged batches persist the operation cursor and counts without progress events or receipts; a final unchanged batch completes through the operation row. Native Jobs still persists scheduling and lease state for restart and resume.

`plan_move` requires source WRITE and DELETE plus target WRITE and validates type, state, field and relation mappings without changing either board. Explicitly dropped fields require no source read. `move` reserves the live, visible source subtree, imports mapped items and links on the target, and finalizes source tombstones through its durable job. Item types select `move_children: move` or `refuse`. Receipts keep phase retries idempotent. Trashed descendants stay on the source. Source tombstones clear value payload and process working data while retaining authorization inputs; source relation aggregates recompute as endpoints move. Source keys follow aliases to the final destination under live destination access; aliases expire with source tombstones. `move_status` reports the durable operation and only readable target ids. Move plans and both move-history forms redact inaccessible peers through the shared peer redactor. Deferred execution rechecks every source item and each mapped noncomputed field, including cleared fields, under the captured operation identity and its live group memberships before importing data. Field-only revocation refuses the move before target import. Repeating a failed operation's key after restoring its authority resumes the same frozen job.

Transition listings for people omit automatic transitions and transitions named only as `run.on_pass`, `on_fail`, `on_cancel` or `on_exhausted` targets. A transition declares `people: true` to offer such an action explicitly; `people: false` hides an ordinary exit. Point reads and awaiting query pages use the same Work rule and the recorded process generation.

A board may override `comments_per_item` in its policy. Deadlines and job/retention throughput are application settings; caller and job deadlines can shorten them. The retention minimum reserves enough units for native slot draining. Invalid values fail validation before a setting commit or schema admission. All retention day windows are integers in 0–106751, the largest whole-day duration representable in signed 64-bit nanoseconds; positive ISO durations share that upper bound and must represent at least one nanosecond. Positive subnanosecond durations return native `INVALID`, including signed/zero-enabled parsing; repeating timers therefore always advance. Parsing validates before integer multiplication. Audit and interval zero values still select 365 days. Every WIP policy key must name a state in the compiled processes; state removal must update its WIP policy in the same declaration.

The initial schema provides `(board_id,item_id,comment_id)` for purged-item comment cleanup, includes the deleted-comment age index with its comment ID tie-breaker, and provides the incoming relation index `(to_board_id,to_id,board_id,from_id,type)`. Board teardown drains incoming relations from other boards using complete keys in the same 100-row budget before removing the board shell. Both selectors have indexes matching eligibility and order.

Known platform gap: Settings 0.3.8 publishes committed revisions through `kickside.settings:settings_changes`, but Core 0.3.17 retention does not subscribe and Settings exposes no committed-change callback hook. Changing retention settings alone therefore does not re-arm an idle retention service. Work reads committed values on its next owner invocation. The platform must connect committed settings revisions to the existing Core retention notifier; Work adds no watcher or write-path notification.

Rebuild/reindex and rebalance event replay use fixed 500-item protocol bounds, independently of current execution batch settings. The initial schema includes every cleanup tie-breaker in receipt, alias, audit, interval, generation and terminal-operation age indexes. Generation protection uses positive live/trashed item and pending/running job-state seeks per bounded candidate, so an empty active population does not scan retained rows on older SQLite planners. Approval, stage-run, failed-job, item-life, visibility and comment selectors retain their matching complete indexes.

The functional test harness explicitly configures read and command budgets to 60000 ms: data and fixture assertions do not impose a production latency target on shared runners. Deadline tests choose their own setting or earlier caller deadline. The snapshot budget probe advances a clock through the existing deadline imports, checks expiry after snapshot work, and restores the real clock before returning; it never sleeps to reach a read deadline. Production defaults remain 2000 ms for reads and 5000 ms for commands.
